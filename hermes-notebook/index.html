Chapter 01

The agent
loop

What happens between the message arriving and the reply going out.

An agent is a model inside a loop

On its own, the model only returns text. What makes it an agent is the loop around it: Hermes calls the model and, if the reply asks for a tool, runs the tool, puts the result into the conversation and calls the model again. The loop ends only when the model answers in text, when the budget runs out, or when someone interrupts it.

one turn
user message
   │
   ▼
build the system prompt         # or reuse last turn's
   │
   ▼
over 50% of the window? ──yes──▶ compress the middle
   │
   ▼
┌▶ call the model
│     │
│     ├── asked for a tool? ──▶ run it ──▶ result into history ─┐
│     │                                                       │
└─────┼───────────────────────────────────────────────────────┘
      │
      └── answered in text ──▶ save the session ──▶ reply

Where it lives

The name is misleading: run_agent.py is just a facade. The loop is run_conversation() in agent/conversation_loop.py, and each phase of a turn has its own file under agent/turn_*.py: preflight, API call, tool round, error recovery, truncation. There are more than 30. It's the densest part of the code, because it's where everything goes wrong: provider down, reply cut off, tool hanging.

The conversation has an alternation rule

Internally every conversation is in OpenAI format, with four roles: system, user, assistant and tool. Providers require alternation: never two assistant messages in a row, never two user messages in a row. Only tool can repeat, when several tools answer the same request. A provider rejects a history that breaks this rule, and a good part of the turn code exists so it never sends one.

Tools: only the safe ones run in parallel

When the model asks for several tools at once, Hermes splits the batch into segments. Only tools that change nothing run together: reading files, searching the web, looking up past sessions. File reads and writes share a segment only if their paths don't overlap. Everything else, the terminal included, runs one at a time. Results come back in the order the model asked for them, as if everything had run in sequence.

Around each execution sit the plugin hooks pre_tool_call and post_tool_call, with the dangerous-command check in between, which stops and asks for approval. Four tools skip the registry entirely: todo, memory, session_search and delegate_task. The loop handles them directly because they change the agent's own state.

When the loop stops

  • Budget. Every agent has an IterationBudget: 500 iterations for the main agent, 250 for each subagent. A subagent has its own budget and doesn't spend the parent's. When it runs out, the agent stops and returns a summary of what it did.
  • Interrupt. A new message or /stop abandons the call in flight. The half-finished reply is discarded and never enters the history.
  • Provider down. On 429, 5xx or 401/403, Hermes tries the fallback_providers from config.yaml, in order, and carries on with whichever answers.

Two compressions

Before calling the model, if the conversation is over 50% of the window, the compressor summarizes the middle and keeps the last 20 messages intact. The gateway has a second safety net, between turns, at 85%. More in chapter 05.

The docs lag, the code rules

The official guide says that with several tools, they all run in parallel. The code only parallelizes the safe ones. The same guide says 50 iterations per subagent, and the code says 250 since a config migration. When in doubt, open the code.

In the code
  • agent/conversation_loop.py: run_conversation(), the loop.
  • agent/tool_dispatch_helpers.py: which tools may run together and how the batch is split.
  • agent/iteration_budget.py and hermes_cli/config_defaults.py: the budget and the subagent's 250.
  • gateway/run_turn.py: the gateway's 85% compression.
  • Official loop guide, to read with the caveat above.
Chapter 02

Prompt
assembly

What the model reads before your message, and why the order matters.

Built once, reused every turn

The system prompt is not rebuilt on every message. Hermes builds it once at the start of the session, keeps it on the agent, and sends the exact same bytes on every turn. The only thing that triggers a rebuild is compression. Even the date line carries only the day, not the time, so the prompt stays identical from morning to night.

Why: the prefix cache

Providers cache the longest prefix of the request that they have already seen, and charge the cached part at a fraction of the price. It works like Docker layers: change one line near the top and everything after it is rebuilt. So the order of the prompt is the order of how likely each piece is to change. What never changes goes first, and what may change goes last.

Three tiers

system prompt
stable     # same for every session of this agent
  identity (SOUL.md, or the built-in default)
  tool and model guidance, platform hints, pinned skills

context    # depends on the project and the folder
  system_message from the caller
  project file: .hermes.md › AGENTS.md › CLAUDE.md › .cursorrules
  git workspace snapshot

volatile   # most likely to differ on a rebuild
  skills index
  MEMORY.md and USER.md snapshots
  plugin prompt sections, active profile line
  date line, runtime environment (host, cwd)

The project file is first match wins: if there is a .hermes.md, the AGENTS.md is not loaded. And SOUL.md goes into the identity slot only, never twice.

Memory is a snapshot

When the agent saves something with the memory tool mid-session, it goes to disk but does not change the prompt already built. The agent only sees the new memory in its prompt in the next session, or after a compression rebuild. Editing the prompt mid-session would throw the cache away.

What enters per turn goes into the user message

Anything that changes from turn to turn stays out of the system prompt. Gateway context, memory recall and the pre_llm_call hook output are added only at call time and never written into the cached prompt. The pre_llm_call output goes into the current user message, at the end of the request, where it doesn't break the cached prefix. That's why a plugin that injects context, like a company charter, uses pre_llm_call and doesn't touch the system prompt.

Where to customize

  • Who the agent is: SOUL.md.
  • Rules of a repo: the project file (AGENTS.md and friends).
  • Reusable procedures: skills.
  • Durable facts about the user: MEMORY.md and USER.md.
  • Per-platform tone: platform_hints in config.yaml, with append or replace.

Editing agent/prompt_builder.py is a change for every Hermes user, not a customization.

The docs contradict themselves here

The official guide lists the skills index in the volatile tier and, a few lines later, says skills are in the stable tier. The code settles it: the skills index opens the volatile tier, because skills change at runtime. Only pinned skills, resolved once per agent, sit in the stable tier.

In the code
  • agent/system_prompt.py: build_system_prompt_parts(), the three tiers, and build_system_prompt(), built once and cached.
  • _timestamp_line(): date only, so the prompt is byte-stable for the day.
  • agent/prompt_builder.py: build_context_files_prompt() and load_soul_md().
  • Official prompt assembly guide, to read with the caveat above.
Chapter 06

Profiles and
kanban.db

What belongs to each agent, and what they all share.

A profile is an isolated agent

Every Hermes agent is a profile: a directory with everything that belongs to it. The default profile lives in ~/.hermes/, the others in ~/.hermes/profiles/<name>/.

Four files matter:

  • SOUL.md: who the agent is and how it behaves.
  • config.yaml: model, tools and the rest of the configuration.
  • .env: API keys and tokens.
  • state.db: the conversations, in SQLite.
~/.hermes
~/.hermes/
├── kanban.db            # shared by all profiles
├── SOUL.md  config.yaml  .env  state.db   # default profile
└── profiles/
    ├── support/
    │   ├── SOUL.md
    │   ├── config.yaml
    │   ├── .env
    │   └── state.db
    └── tech/
        └── ...

Secrets don't cross profiles

A single gateway can serve several profiles in the same process, so one profile's keys must never leak into another's turn. If some code asks for a secret without knowing which profile it belongs to, Hermes doesn't fall back to the global environment: it raises UnscopedSecretError and stops.

Why it matters is prompt injection. The agent that talks to strangers the most should have the least power. The support bot talks to any customer, so whatever someone writes to it must not reach the tech bot's keys.

kanban.db is what they share

Outside the profiles, at the root, sits ~/.hermes/kanban.db. It's the only place common to all of them. When one agent hands work to another, it opens a task on the board with the other profile as assignee, and the kanban dispatcher delivers the task to it.

kanban.db · tasks
id          t_3a91c0de
title       "500 error on the customer report"
created_by  support
assignee    tech
status      ready   # triage · todo · ready · running · blocked · done ...

That's the default board. You can create other boards under ~/.hermes/kanban/boards/<name>/, and an agent working on one board can't see the others.

In the code
  • hermes_constants.py: get_hermes_home() resolves the active profile's directory, and _PROFILE_IDENTITY_MARKERS lists the files that make a directory a profile.
  • agent/secret_scope.py: the per-profile secret scope and UnscopedSecretError.
  • hermes_cli/kanban_db.py: kanban_db_path(), the default board at the root and the others under kanban/boards/.
